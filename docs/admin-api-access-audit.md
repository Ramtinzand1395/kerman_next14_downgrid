# گزارش تطبیق دسترسی صفحات و API

تاریخ: ۵ نوامبر ۲۰۲۶ — برنچ: `fix/admin-api-access-policy`

مبنای بررسی: آخرین `main` با commit برابر `ecf757419808fcf44ccd3965cd5e0419c846aec5`.

## نتیجه و شواهد قبل از اصلاح

ایراد تأیید و با اجرای کد بازتولید شد. Middleware نقش `admin` را به سفارش حضوری و مرکز اعلان‌ها محدود می‌کرد، اما `requireAdmin` هر دو نقش `admin` و `superadmin` را می‌پذیرفت.

- با نشست شبیه‌سازی‌شدهٔ `admin`، اجرای handler واقعی `GET /api/admin/shipping-settings` پاسخ `200` داد و سرویس خواندن تنظیمات فراخوانی شد.
- اجرای handler واقعی `POST /api/admin/loyalty/xp` با همان نقش، پاسخ `200` داد و سرویس آزمایشی اعطای امتیاز فراخوانی شد.
- در `getOrderForViewer`، نقش `admin` شرط مالکیت سفارش آنلاین را از query حذف می‌کرد؛ این امکان در API جزئیات سفارش، صفحه فاکتور و صفحه موفقیت پرداخت استفاده می‌شد.

دو سرویس بالا و دیتابیس در بازتولید اولیه mock بودند. هیچ امتیاز واقعی اعطا یا دادهٔ واقعی تغییر داده نشد.

## اصلاحات

- سیاست مشترک در `lib/dashboard-access.ts` تعریف و در middleware، guard مدیریت و دسترسی سفارش استفاده شد.
- `requireAdmin` اکنون فقط `superadmin` را می‌پذیرد. نام آن برای سازگاری با مصرف‌کنندگان فعلی حفظ شد؛ تمام مصرف‌کنندگان فعلی مدیریت بخش‌های مخصوص مالک هستند.
- بررسی نشست و نقش پیش از اتصال به MongoDB انجام می‌شود: بدون نشست `401` و با نقش غیرمجاز `403`.
- از ۲۹ مسیر / ۵۴ عملیات استفاده‌کننده از guard، دو مسیر / چهار عملیات promotion-modal پیش‌تر بررسی اضافی `superadmin` داشتند. اصلاح حاضر دسترسی نامجاز را در ۲۷ مسیر / ۵۰ عملیات دیگر می‌بندد: باشگاه مشتریان، کیف پول و امتیاز، گزارش‌ها، پاداش مراجعه، تنظیمات ارسال، تنظیمات و مدیریت درخواست نصب/پیک و لینک پرداخت آن‌ها.
- فقط `superadmin` می‌تواند شرط مالکیت سفارش آنلاین را رد کند؛ سایر نقش‌ها همچنان سفارش متعلق به خود را می‌بینند.
- تطبیق مسیر صفحات با مرز `/` انجام می‌شود تا نام‌هایی مثل `/dashboard/store-order-export` اشتباهاً مجاز نشوند.

| نقش | صفحات مدیریتی حساس | APIهای مدیریتی بررسی‌شده | سفارش آنلاین دیگران | سفارش حضوری |
|---|---|---|---|---|
| `superadmin` | مجاز | مجاز | مجاز | مجاز |
| `admin` | انتقال به سفارش حضوری | `403` | غیرقابل مشاهده | مجاز |

## اعتبارسنجی

- ۳۷ تست جدید پاس شد؛ از جمله اجرای ۵۴ عملیات API با شش وضعیت نشست/نقش (۳۲۴ فراخوانی)، بررسی تمام ۱۵ صفحه داشبورد، مرز مسیرها، حفظ ویرایش سفارش حضوری، عملیات مجاز `superadmin` و مالکیت سفارش آنلاین.
- `npm test`: تعداد ۱۸۱ تست موفق، صفر شکست و یک تست اختیاری POS با replica set محلی skip شد.
- `npx tsc --noEmit`: موفق.
- `npm run build`: موفق؛ هشدار قبلی `<img>` در Footer همچنان وجود دارد.
- آزمایش HTTP روی production build محلی: ۱۶۲ درخواست API برای `admin`، `user` و بدون نشست، همراه هشت بررسی صفحه، موفق بود. در این مرحله نشست‌های JWT آزمایشی توسط NextAuth واقعی اعتبارسنجی شدند؛ guard و middleware mock نبودند.

اجرای مجدد:

```bash
node --test admin-access-policy.test.mjs
npm test
npx tsc --noEmit
npm run build
node scripts/check-admin-access-http.mjs
```

اسکریپت HTTP سرور محلی روی پورت ۳۱۰۷ راه می‌اندازد، کلید نشست تصادفی می‌سازد و URI دیتابیس را به مقصد loopback غیرقابل اتصال محدود می‌کند. بنابراین حتی بازگشت ایراد دسترسی نمی‌تواند به دیتابیس واقعی بنویسد.

## حدود بررسی

ورود با حساب واقعی کارمند، ارسال OTP و درخواست به production انجام نشد. تست مثبت عملیات داده‌ای `superadmin` و سفارش حضوری با سرویس/مدل mock اجرا شد. این گزارش ممیزی کامل امنیت تمام endpointهای پروژه نیست. تغییرات فقط برای برنچ جدید آماده شده‌اند؛ merge یا deploy به `main` انجام نشده است.
