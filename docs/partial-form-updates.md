# اصلاح ذخیرهٔ جزئی فرم‌های مدیریتی

برنچ: `fix/admin-api-access-policy` — ۵ نوامبر ۲۰۲۶

## یافته‌ها و اصلاحات

اسکیمای ساخت با default برای ویرایش جزئی هم استفاده می‌شد. در Zod 4، استفاده از `partial()` روی همین اسکیمای دارای default کافی نیست: فیلد ارسال‌نشده می‌تواند مقدار پیش‌فرض بگیرد و با `$set` روی داده فعلی نوشته شود. این ایراد در پنج فرم دیگر باشگاه بازتولید شد. در دو مسیر دیگر نیز تبدیل ورودی ناقص به رشته خالی یا null، همین نتیجه را داشت.

| فرم | رفتار مشکل‌دار | رفتار اصلاح‌شده |
|---|---|---|
| جایزه گردونه | تغییر وضعیت می‌توانست مبلغ و ترتیب را صفر کند؛ تغییر عنوان می‌توانست وضعیت را فعال کند. | فقط فیلدهای ارسال‌شده ذخیره می‌شوند. |
| نشان‌ها | پاداش XP و ترتیب صفر و وضعیت فعال می‌شد. | پاداش، ترتیب و وضعیت ارسال‌نشده حفظ می‌شوند. |
| کش‌بک | محدودیت دسته و VIP پاک، حداقل خرید و اولویت صفر می‌شد. | تمام محدودیت‌های ارسال‌نشده حفظ می‌شوند. |
| کمپین باشگاه | ضریب XP، پاداش مشارکت و ساعات دسترسی زودتر بازنشانی می‌شد. | این مقادیر با ویرایش عنوان یا وضعیت تغییر نمی‌کنند. |
| مأموریت | وضعیت بازنشانی می‌شد؛ ویرایش یک جزء پاداش می‌توانست بقیه پاداش و کوپن متصل را پاک کند. | اسکیمای ویرایش بدون default است و فقط جزء ارسال‌شدهٔ پاداش نوشته می‌شود. |
| سطوح و VIP | نوشتن کل آبجکت `benefits` با یک مقدار، سایر مزایا را حذف یا بازنشانی می‌کرد. | فقط مسیر همان مزیت، مثلاً `benefits.discountPercent`، به‌روز می‌شود. |
| سئوی دسته | ویرایش فقط عنوان، سایر متن‌ها و FAQها را خالی می‌کرد. | فیلدهای ارسال‌نشده حفظ می‌شوند. |
| فهرست بازی | ویرایش نام با ورودی ناقص، حجم، قیمت و فضای ذخیره‌سازی را null می‌کرد. | اسکیمای ویرایش مستقل، مقادیر ارسال‌نشده را حفظ می‌کند؛ تصویر نیز همچنان حفظ می‌شود. |

برای پنج فرم باشگاه، فیلدهای پایه بدون default تعریف شدند؛ defaultها فقط در اسکیمای ساخت اعمال می‌شوند. نام exportهای قبلی حفظ شده است. اسکیمای ویرایش پاداش مأموریت نیز مستقل از defaultهای ساخت و به‌صورت جزئی تعریف شده است. مسیرهای پاداش مأموریت و مزایای عضویت با `$set` نقطه‌ای و بعد از اعتبارسنجی whitelist به‌روز می‌شوند، تا دیگر اجزای همان آبجکت باقی بمانند.

مقدار صریح `0` یا `false` همچنان ذخیره می‌شود. پاک‌کردن صریح دسته‌ها با `[]`، متن سئو با `""` و مقدار بازی با `null` نیز پشتیبانی می‌شود. مقدار پیش‌فرض هنگام ساخت رکورد جدید تغییری نکرده است.

تنظیمات عمومی باشگاه قبلاً از مسیرهای نقطه‌ای استفاده می‌کرد و ویرایش قوانین پاداش مراجعه نیز قبلاً داده فعلی را ادغام می‌کرد؛ برای این دو، تغییر ناشی از همین الگو لازم نبود. این بررسی، ممیزی الگوی ذخیره جزئی و تبدیل مقادیر ارسال‌نشده است و ادعای بررسی تمام خطاهای احتمالی فرم‌های سایت نیست.

## آزمایش

تست‌های جدید پیش از اصلاح اجرا شدند: از ۱۵ تست اولیه، ۱۰ تست شکست خورد و پنج تست سازگاری ساخت موفق بود. پس از اصلاح، همهٔ آن‌ها و دو تست تکمیلی موفق شدند.

۱۷ تست جدید در `form-partial-updates.test.mjs` موارد زیر را پوشش می‌دهد:

- اسکیمای واقعی و handler واقعی ویرایش برای پنج فرم باشگاه، سئوی دسته و فهرست بازی؛ مدل‌های ذخیره‌سازی mock هستند.
- حفظ مقادیر موجود هنگام ویرایش عنوان یا وضعیت، حفظ defaultهای ساخت و حفظ اجزای دیگر پاداش/مزایا.
- امکان اعمال صفر، false، آرایه خالی، رشته خالی و null صریح در فیلدهای مجاز.
- رد داده نامعتبر پیش از نوشتن و جلوگیری از عبور کلیدهای ناشناخته/اپراتورمانند در پاداش.

نتیجهٔ نهایی: `npm test` با ۲۰۹ تست موفق، صفر شکست و یک تست اختیاری POS اجرا‌نشده؛ `npx tsc --noEmit` و `npm run build` نیز موفق بودند. هشدار قبلی استفاده از `<img>` در Footer در build باقی است.

اجرای تست اختصاصی:

```bash
node --test form-partial-updates.test.mjs
```

هیچ دیتابیس واقعی خوانده یا تغییر داده نشد. داده‌هایی که پیش‌تر بازنشانی شده‌اند از روی حدس بازسازی نشده‌اند. این تغییرات فقط در همین برنچ ثبت می‌شوند و merge یا deploy به `main` انجام نمی‌شود.
