# پرداخت خدمات در جزئیات ادمین و گزارش مالی

برنچ: `fix/admin-api-access-policy`

## مشکل تأییدشده

- API جزئیات، `payment` را برمی‌گرداند، ولی پنجرهٔ ادمین فقط شیء ردیف جدول را نمایش می‌داد؛ باز کردن پنجره یا بازگشت از پرداخت دادهٔ جدید دریافت نمی‌کرد.
- وضعیت `initiating` به‌اشتباه پرداخت‌نشده نمایش داده می‌شد. مبلغ و زمان پرداخت نیز در جزئیات نبود.
- بخش مالی خدمات تنها `pricing.serviceFinalAmount` درخواست‌های تکمیل‌شده را جمع می‌زد و هنوز می‌گفت مدل خدمت سند پرداخت ندارد.

## تغییرات

- جزئیات با باز شدن، دکمهٔ به‌روزرسانی و بازگشت فوکوس به پنجره، از GET موجود `/api/admin/appointments/:id` دادهٔ تازه می‌گیرد. درخواست قبلی هنگام بستن یا تعویض درخواست لغو می‌شود و پاسخ دیررس نمی‌تواند اطلاعات درخواست دیگر را جایگزین کند.
- پنج وضعیت پرداخت، کد پیگیری زرین‌پال، مبلغ ثبت‌شدهٔ پرداخت به تومان و زمان پرداخت تهران نمایش داده می‌شوند. کد پیگیری درخواست در سربرگ جدا باقی می‌ماند. این نمایش به وجود قیمت‌گذاری یا پیک وابسته نیست.
- خطای دریافت دادهٔ جدید با هشدار قدیمی‌بودن اطلاعات و امکان تلاش مجدد نمایش داده می‌شود.
- `appointments.totals` و نقاط نمودار دو فیلد افزوده دارند: `servicePaidAmount` و `paidAppointments`. فقط اسناد با `payment.status=paid`، مبلغ عددی غیرمنفی و تاریخ پرداخت داخل بازه وارد محاسبه می‌شوند.
- منبع مبلغ `payment.amount` به تومان و منبع تاریخ `payment.paidAt` است. قیمت روز، مبلغ پیشنهادی، تاریخ رزرو یا تاریخ تکمیل جایگزین آن‌ها نمی‌شود. یک سند درخواست یک بار جمع می‌شود؛ وضعیت اداری بعدی هم سند پرداخت ثبت‌شده را حذف نمی‌کند.
- مبلغ پرداخت خدمات هزینهٔ پیک را نیز شامل می‌شود؛ هزینهٔ پیک دوباره به آن اضافه نمی‌شود. این عدد دریافتی ثبت‌شده است، نه سود خالص یا عدد پس از استرداد؛ مدل خدمات فعلی سابقهٔ استرداد ندارد.
- قیمت‌گذاری خدمت، پیک و تخفیف‌ها با تاریخ تکمیل، جدا از دریافتی واقعی باقی می‌مانند. کارت، نمودار و جدول خدمات از اطلاعات پرداخت استفاده می‌کنند. گزارش محصولات و سفارش‌های دستی قرارداد مستقل خود را حفظ می‌کنند.
- پرداخت فاقد مبلغ یا تاریخ معتبر به‌صورت تخمینی درآمد تلقی نمی‌شود. هیچ مهاجرت یا بازنویسی اطلاعات قدیمی انجام نشده است.

## آزمون

```bash
APPOINTMENT_LOCAL_REPORT_TESTS=true node --test appointment-financial-report.test.mjs
APPOINTMENT_LOCAL_REPORT_TESTS=true npm test
npx tsc --noEmit
npm run build
```

آزمون مالی از MongoDB موقت روی `127.0.0.1` و دادهٔ ساختگی استفاده می‌کند و هیچ‌گاه `MONGODB_URI` را نمی‌خواند. این بخش با متغیر بالا فعال می‌شود تا اجرای عادی تست‌ها دانلود باینری MongoDB را تحمیل نکند.

سناریوهای مالی: تفاوت مبلغ پرداخت و قیمت‌گذاری، پرداخت نصب و تعمیر حضوری، شمول پیک فقط یک بار، پرداخت بعد از تاریخ تکمیل، حذف وضعیت‌های غیرموفق و دادهٔ ناقص، مرز نیمه‌باز بازه، نیمه‌شب تهران، گزارش خالی و تغییر وضعیت اداری پس از پرداخت.

تست رندر واقعی پنجره، پنج وضعیت و نمایش مبلغ، زمان و کد پیگیری را بدون نیاز به پیک یا قیمت‌گذاری بررسی می‌کند. آزمون مرورگر محلی نیز دریافت تازه هنگام باز شدن، به‌روزرسانی دستی، فوکوس، خطا و تلاش مجدد، پاسخ دیررس درخواست قبلی، و جدول گزارش را در عرض‌های ۳۹۰ و ۱۳۶۳ پیکسل بررسی می‌کند.

این آزمون‌ها پرداخت واقعی ایجاد نکرده و دیتابیس سایت را تغییر نداده‌اند. تغییرات فقط روی برنچ فوق هستند؛ `main` و سایت زنده تغییر نکرده‌اند.

نتیجهٔ اجرا: ۲۳۰ تست کل؛ ۲۲۹ موفق و یک تست اختیاری POS اجرا نشده است. هر ۸ تست مجموعهٔ مالی جدید، شامل زیرآزمون‌های MongoDB، پاس شدند. آزمون مرورگر در هر دو عرض پاس شد و سرریز افقی دیده نشد. TypeScript و بیلد production موفق بودند؛ تنها هشدار بیلد، هشدار قبلی تصویر Footer بود.
