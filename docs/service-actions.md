# مقصد دکمه‌های صفحهٔ خدمات

برنچ: `fix/admin-api-access-policy`

قبلاً هر پنج کارت صفحهٔ `/services` بدون توجه به عنوان دکمه به `/contact-us` می‌رفتند. اکنون مقصد هر کارت همراه دادهٔ همان خدمت تعریف می‌شود:

| دکمه | مقصد و رفتار |
| --- | --- |
| مشاهده بازی‌های اکانتی | `/category/account-games`، صفحهٔ دستهٔ بازی اکانتی |
| دریافت مشاوره خرید | فرم تماس با موضوع «مشاوره خرید بازی و کنسول» |
| ارسال درخواست ارزیابی کنسول | فرم تماس با موضوع «درخواست ارزیابی کنسول کارکرده» |
| بررسی شرایط ارسال | `/terms#shipping`، بخش ارسال و تحویل قوانین |
| ارتباط با پشتیبانی | فرم تماس با موضوع «پشتیبانی پس از خرید» |
| دریافت مشاوره خدمات | فرم تماس با موضوع «مشاوره خدمات» |

موضوع تماس از پارامتر `topic` و فهرست محدود موضوع‌های پشتیبانی‌شده تعیین می‌شود. عنوان و فیلد موضوع فرم متناسب با درخواست هستند؛ موضوع برای کاربر قابل ویرایش است. موضوع نامعتبر یا آرایه‌ای، فرم عمومی را باز می‌کند.

متن و فیلدهای کاربر با تغییر موضوع پاک نمی‌شوند. پیش‌نویس ورود، موضوع انتخابی و ویرایش کاربر را در بازگشت به همان درخواست حفظ می‌کند؛ برای خدمت دیگر، موضوع جدید اعمال و سایر اطلاعات پیش‌نویس حفظ می‌شوند. دادهٔ داخلی پیش‌نویس در درخواست POST ارسال پیام قرار نمی‌گیرد و قرارداد API تماس تغییری نکرده است.

اعتبارسنجی:

```bash
node --test service-cta.test.mjs
APPOINTMENT_LOCAL_REPORT_TESTS=true npm test
npm run build
```

پنج تست جدید، مقصد دکمه‌ها، موضوع‌های معتبر و نامعتبر، حفظ متن هنگام تغییر موضوع، بازیابی پیش‌نویس ورود و قرارداد ارسال پیام را بررسی می‌کنند. تست مرورگر با MongoDB موقت روی loopback و دادهٔ ساختگی انجام می‌شود؛ ارسال پیام و پاسخ حساب کاربری در مرورگر شبیه‌سازی می‌شوند. هیچ پیام واقعی ارسال و هیچ داده‌ای در دیتابیس سایت تغییر داده نمی‌شود.

نتیجه: ۲۳۵ تست کل؛ ۲۳۴ موفق و یک تست اختیاری POS اجرا نشده است. بیلد، بررسی TypeScript و lint موفق بودند؛ تنها هشدار بیلد مربوط به تصویر Footer از قبل بود. هر شش مقصد، موضوع‌های فرم، پرش به بخش ارسال، رفت‌وبرگشت ورود و ارسال فرم در عرض‌های ۳۹۰ و ۱۳۶۳ پیکسل با موفقیت بررسی شدند و سرریز افقی دیده نشد.
